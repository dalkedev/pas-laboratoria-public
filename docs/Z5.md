# Zadanie 5 — mycloud

Prywatny dysk znajduje się pod `/z5/`. Korzysta z istniejących kont `users`, sesji, Bootstrapa i lokalnego UAParser.js. Po rejestracji powstaje pusty katalog nazwany loginem użytkownika. Pierwsze wejście istniejącego użytkownika z wcześniejszego zadania również tworzy jego prywatny katalog. Konto i katalog są powiązane z identyfikatorem użytkownika w prywatnym pliku metadanych; ponowne utworzenie usuniętego konta o tym samym loginie nie przejmuje dawnych plików.

| Wymaganie | Realizacja |
|---|---|
| Lista plików i katalogów po logowaniu | `index.php`, osobny katalog każdego użytkownika |
| Jeden poziom podkatalogów i powrót wyżej | Parametr `dir` zawiera jedną nazwę, bez separatorów ścieżki; tworzenie katalogu jest dostępne wyłącznie w katalogu głównym |
| Tworzenie i usuwanie | POST `mkdir.php` i `delete.php`, token CSRF; niepusty katalog wymaga uprzedniego usunięcia zawartości |
| Wysyłanie dowolnego typu pliku | `select.php` → POST `upload.php`, pole `fileToUpload`; oryginalne bajty bez przekodowania |
| Pobieranie | Uwierzytelniany `file.php`, nazwa pliku w `Content-Disposition`, bez bezpośrednich adresów do magazynu |
| Obrazy, audio i wideo | Miniatury i `view.php`, odtwarzacze HTML z przyciskami sterowania, bez autoplay; pojedyncze żądania Range obsługują przewijanie |
| Inne formaty, także PDF, DOCX, SVG i PHP | Pobieranie jako załącznik; plik PHP nie jest wykonywany, a przesłany SVG nie jest renderowany jako aktywny dokument |
| Poprawne i błędne logowania | Osobne rekordy w `goscieportalu`; historia bieżącego konta pod `logowania.php` |
| Rejestr wizyt i parametry przeglądarki | Rekord wizyty oraz aktualizacja metryk JSON powiązana z sesją, tokenem CSRF i jednorazowym nonce |

## Konfiguracja

`CLOUD_STORAGE_ROOT` wskazuje bezwzględny, zapisywalny katalog poza document root. Domyślnie jest to `storage/mycloud` obok `app` oraz `public` lub `public_html`. Przykładowy układ hostingu:

```text
katalog-domeny/
├── app/
├── public_html/
└── storage/
    ├── mycloud/
    │   └── login-użytkownika/
    └── .mycloud-meta-.../
```

Cały `storage/` musi przetrwać aktualizację aplikacji. Katalogi są prywatne (`0700`), a pliki danych i metadanych mają `0600`. Metadane i blokady znajdują się obok `mycloud`, dlatego przy kontenerach należy zachować cały katalog nadrzędny `storage`. Magazyn nie należy do Gita ani paczki kodu aplikacji.

Operacje sprawdzają właściciela katalogu, odrzucają dowiązania symboliczne, wyjście poza katalog oraz nadpisywanie istniejących nazw. Blokada per użytkownik porządkuje współbieżne operacje, a zapis w trybie wyłącznego tworzenia chroni istniejący plik także podczas równoczesnych uploadów. Nazwy muszą być poprawnym UTF-8, mieścić się w 255 bajtach i nie zawierać separatorów, znaków sterujących ani wartości `.` lub `..`.

Aplikacja nie wprowadza limitu rozmiaru pliku ani listy dozwolonych rozszerzeń dla dysku. Nadal obowiązują ograniczenia PHP, serwera HTTP, czasu żądania, miejsca i limitu konta hostingowego. Lokalne PHP ma `upload_max_filesize=0`, `post_max_size=0`, a nginx `client_max_body_size 0`. Na hostingu należy sprawdzić rzeczywiste ustawienia operatora; lokalna konfiguracja nie zmienia limitów zdalnego serwera. Osobne ograniczenia opcjonalnego avataru pozostają takie jak w wcześniejszych zadaniach.

## Baza

Migracja `database/z5.sql` idempotentnie dodaje do istniejącej tabeli `goscieportalu` cztery nullable kolumny: `application`, `event_type`, `login_name` i `login_success`. Używa składni zgodnej z MySQL 5.7 i zachowuje dotychczasowe rekordy oraz działanie wcześniejszych zadań. Wizyty zadania 5 mają `application='z5'`, `event_type='visit'`. Zdarzenia logowania mają `event_type='login'`, nazwę konta oraz `login_success` równy `1` lub `0`; nie zapisują hasła. Data i godzina pochodzą z bazy.

Przed uruchomieniem aplikacji na istniejącej bazie trzeba wykonać tę migrację. Limiter nieudanych logowań pozostaje wspólnym mechanizmem poprzednich zadań. Opcjonalny wariant trzech prób z tabelą `break_ins`, współdzielenie plików, dalsze poziomy katalogów i dodatkowa aplikacja desktopowa nie należą do tej realizacji.

## Weryfikacja

Testy `tests/z5_smoke.py` obejmują dwa konta, izolację magazynów, katalogi, dowolne bajty plików, media, zakresy HTTP, ochronę przed nadpisaniem, CSRF i manipulacją ścieżkami. Rzeczywiste wyniki uruchomień oraz status wdrożenia znajdują się w `docs/VERIFICATION.md`. Samo przygotowanie kodu, migracji lub paczki nie potwierdza opublikowania tej wersji na hostingu.

Ustawienia rozmiarów zweryfikowano z [PHP — core ini](https://www.php.net/manual/en/ini.core.php), [źródłem PHP 8.4 obsługującym upload](https://github.com/php/php-src/blob/PHP-8.4/main/rfc1867.c) oraz [nginx — client_max_body_size](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size). Limity lokalne nie ustalają limitów operatora hostingu.
